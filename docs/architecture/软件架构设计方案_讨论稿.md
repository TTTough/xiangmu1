## 0 结论摘要

1. **实际架构是“单进程 Flask 单体 + 服务端渲染页面 + 同源 JSON API + 单个 SQLite 文件库 + 进程内守护线程 + 数据库触发器兜底”**。没有独立前端工程、没有独立服务层、没有消息队列、没有外部数据库或外部认证。
2. **分层只在文件和注释层面成立**：`templates/` 是表现层，`create_app()` 内的 67 个路由是接口层，模块级业务函数是业务层，`db.py` + 内联 SQL 是数据访问层，但四层全部围绕一个 `app.py` 与 Flask 请求上下文组织，业务函数直接依赖 `g`、`request`、`session`、`current_app`。
3. **需求覆盖是“AC 驱动”的**：68 条 AC 均有对应测试映射，`74 passed` 可复现；但按 FR 功能点逐条核对，仍有约 10 处“文档有、代码无”或“代码有、文档未定”，集中在管理员代创建、预约修改、黑名单直接加入/延期、投诉回避与时限、用户信息管理、统计维度、参数生效边界。
4. **非功能需求基本按“单机课程演示”实现**：NFR-02/04/06/14/15 没有压测、监控、备份、保留与清理证据；NFR-05 靠 SQLite 写锁与触发器保证单机正确，不能外推为生产并发能力。
5. **最需要先确认的不是技术选型，而是验收口径**：这套系统按“演示基线”验收，还是按 SRS 写的 500 并发、99.5% 可用、每日备份、真实 SSO 验收。这个口径决定后面绝大多数 Q 的取舍（见 Q-23、Q-24、Q-47）。

### 3.3 一次请求的调用链（以创建预约为样本）

```text
浏览器 POST /api/reservations
  → before_request: 从 session 取 user_id，装载 g.user        app.py:4107-4119
  → role_required("student"): 会话空闲校验 + 角色判定           app.py:262-276
  → 路由闭包 api_create_reservation: 取 JSON 载荷               app.py:4654-4664
  → create_reservation:
       BEGIN IMMEDIATE                                        db.py:56-65
       账号状态/黑名单 → 有效预约上限 → 时间/时长/开放/提前天数
       → 座位存在/停用 → 时段冲突（SELECT）
       → INSERT reservations（触发器二次兜底）                 schema.sql:267-296
       → UPDATE seats.status
       → INSERT notifications
       → INSERT audit_logs
       COMMIT
  → 返回 201 JSON；失败时 record_reservation_failure 另写拒绝审计
```

这条链路体现的是“**事务脚本（Transaction Script）**”风格：一个业务动作 = 一个函数 = 一段显式流程，而不是领域模型 + 仓储 + 应用服务。

### 3.4 横切机制

| 机制 | 实现 | 证据 | 评价 |
|---|---|---|---|
| 会话 | `before_request` 装载用户；空闲超时读 P-17；`session.clear()` 后跳登录 | `app.py:231-248`、`app.py:4107-4119` | 简单有效；无服务端会话表，无法强制单会话 |
| 角色权限 | `role_required(*roles)` + 对象级 `require_room_access` | `app.py:262-276`、`app.py:180-207` | 服务端校验到位；管理员授权范围来自额外表 |
| 内容协商 | `/api/` 或 Accept JSON 返回 JSON，否则渲染 `error.html` | `app.py:64-69`、`app.py:4128-4143` | 同一路由服务页面与 API；错误格式统一 |
| 统一错误 | `ApiError(status, code, message)` | `app.py:54-61` | 业务码清晰；无错误码字典文档之外的枚举约束 |
| 审计 | 与业务写同一事务；`audit_logs` 触发器禁改删 | `db.py:93-129`、`schema.sql:299-309` | 覆盖 29 类动作；失败操作也留痕（预约/取消） |
| 参数 | 运行时一律 `SELECT rule_params`，不读 `config.py` 默认值 | `db.py:68-82` | 改库即生效；但 11 项参数没有消费点，见 Q-32 |
| 时间 | `get_now()` 统一服务端时钟；测试注入 `NOW_PROVIDER` | `app.py:72-78`、`tests/conftest.py:28-48` | NFR-18 落实较好；无时区/夏令时处理 |
| 脱敏 | 姓名、学号、联系方式在输出层脱敏 | `app.py:139-166` | 覆盖记录、实时视图、投诉详情；导出未实现 |
| 事务 | 写操作统一 `immediate_transaction` | `db.py:56-65` | SQLite 单写者模型下正确；高并发会排队 |

### 3.5 分层评价

- **优点**：单文件降低了部署与演示成本；业务函数命名清晰、注释带需求编号，需求追溯性好；测试用假时钟和临时库，NFR-13 基本满足。
- **代价**：`app.py` 5,012 行，任一改动都要在同一文件内回归；业务函数依赖请求上下文，无法脱离 Flask 单独单元测试；页面与 API 双出口导致参数解析重复；无迁移机制，版本间只能复制目录。
- 这不是“错误架构”，而是**演示优先的取舍**。是否在课程剩余时间内拆分，属于 ADR-01，不应由本稿决定。

### 4.2 关系（实现视角）

```text
rooms 1─* zones 1─* seats 1─* reservations 1─0..1 checkins
                                  │
                                  ├─* violations（reservation_id 可空，V3 可无预约）
                                  └─* notifications（按 user）

users 1─* reservations / violations / blacklists / evaluations / complaints / notifications
users 1─* audit_logs（actor）
users *─* rooms  via admin_room_assignments

rule_params：独立配置表，无外键
```

`reservations` 同时冗余 `room_id`、`zone_id`，用于按自习室统计与授权过滤，避免每次 JOIN；代价是座位换房间时需同步维护（当前无此操作）。

### 4.3 不变量与数据库兜底

| 不变量 | 应用层 | 数据库层 |
|---|---|---|
| 同一座位同一日期时段至多一条有效预约（NFR-05） | `BEGIN IMMEDIATE` + 冲突 SELECT | `trg_reservations_no_overlap_insert/update`，`RAISE(ABORT,'SEAT_TIME_CONFLICT')`（`schema.sql:267-296`） |
| 同预约同违约类型不重复（BR-11） | `_create_auto_violation` 先查后插 | 部分唯一索引 `uq_violations_reservation_type`（`schema.sql:135-137`） |
| 通知不可删除（AC-12-02） | `DELETE` 路由显式 403 | `trg_notifications_no_delete`（`schema.sql:171-175`） |
| 审计不可改删（BR-24） | `PUT/PATCH/DELETE` 路由显式 403 | `trg_audit_logs_no_update/delete`（`schema.sql:299-309`） |

## 5 接口架构

### 5.1 规模与分布

- 路由总数 **67**：页面路由 26 个，JSON API 41 个。
- 其中 4 个是“显式拒绝型”端点：直接改写座位状态、修改/删除审计日志、删除通知、旧版手动违约路径（410）。
- 无 API 版本前缀、无 OpenAPI/Swagger 文档、无统一请求 ID、无速率限制。
- 页面与 API 共享同一套会话 Cookie 与错误处理。

### 5.2 约定

| 约定 | 内容 | 证据 |
|---|---|---|
| 成功响应 | JSON 对象，含 `message` 与业务对象（创建类返回 201） | `docs/api.md` |
| 失败响应 | `{"error":{"code","message"}}`，中文可读说明 | `app.py:4128-4143` |
| 状态码 | 400 参数、401 未登录、403 越权、404 不存在、409 业务冲突、410 旧接口、423 锁定 | `docs/api.md:689-698` |
| 认证 | Flask 签名 Cookie；登录成功 `session.clear()` 后写 `user_id/role` | `app.py:4203-4207` |
| 权限 | 角色装饰器 + 对象归属/自习室授权校验；失败不产生数据变更 | `app.py:210-276` |
| 分页 | `page`/`page_size`；记录默认 10、审计默认 20、上限 100 | `app.py:2880-2891` |
| 时间格式 | 日期 `YYYY-MM-DD`，时刻 `HH:MM`，时间戳 `YYYY-MM-DD HH:MM:SS` | `app.py:81-108` |
| 审计 | 写操作同事务写 `audit_logs`；失败预约/取消失败也写 | `app.py:924-947` |

### 5.3 权限模型

- **角色级**：`role_required("student"|"admin"|"sysadmin"|"logistics")`，按 URL 前缀分组。
- **数据级**：学生只取本人记录；管理员通过 `admin_room_assignments` 限定自习室；系统管理员与后勤为全量只读。
- **对象级**：`require_room_access`、`require_seat_access` 对资源、实时视图、V3、座位历史生效。
- **不一致点**：权限矩阵第 15/16 行给系统管理员资源维护权限，但 `/api/admin/*` 全部只允许 `admin`，见 Q-13；矩阵第 2/26 行的用户信息查看/修改没有对应接口，见 Q-38。

### 5.4 接口层缺口

- 无幂等键或请求指纹，EX-01 的“相同参数重复请求只创建一条”没有专门实现，见 Q-36。
- 无 CSRF Token；仅靠 `SameSite=Lax` 与 JSON 请求体降低风险。
- 无请求体大小限制、无登录接口限流（仅账号锁定）。
- 页面内联 JS 直接把业务错误 `message` 显示给用户，符合 NFR-17；但未统一做字段级错误定位。

## 9 ADR 候选（提议，待评审）

> 以下只列备选与代价，**不作决定**。状态统一为“提议（待评审）”。

### ADR-01 单体形态：保留单文件还是按域拆分

- 背景：`app.py` 5,012 行，业务函数与 Flask 上下文耦合；课程剩余时间有限。
- 备选 A：保留单文件，只做“函数分组 + 注释索引 + 禁止跨组调用”的软约束。代价：改动仍集中，审查困难；收益：零迁移风险。
- 备选 B：拆为 `routes/`、`services/`、`repositories/`、`models/`。代价：需要重写导入、测试与部署路径，回归量大；收益：可独立测试、多人并行。
- 验证：以“修改一个预约规则需要触碰几个文件/跑多少测试”为度量。
- 重开条件：多人同时修改预约/违约核心逻辑，或需要单元测试替代接口测试。

### ADR-02 持久化：SQLite 还是 PostgreSQL

- 背景：NFR-04/05 与并发写入；当前单机演示。
- 备选 A：继续 SQLite（WAL + `BEGIN IMMEDIATE` + 触发器）。代价：单写者、无网络访问、迁移工具缺；收益：零运维、演示稳定。
- 备选 B：PostgreSQL（唯一/排他约束、连接池、迁移工具）。代价：环境依赖、部署复杂、课程环境未必允许；收益：并发与生产语义更接近 SRS。
- 验证：多连接并发抢座测试；目标 50 次/秒写入是否可达。
- 重开条件：验收要求真实并发或多人远程访问。

### ADR-03 接口风格：SSR+fetch 混合还是纯 SPA/纯 SSR

- 背景：26 个页面 + 41 个 API；页面内联 JS。
- 备选 A：维持混合。代价：双出口重复解析、前端无构建；收益：改动小、演示直观。
- 备选 B：统一为纯 SSR（表单提交）。代价：10 秒局部刷新需改写；收益：无 JS 依赖。
- 备选 C：纯 SPA。代价：引入前端工程与构建链，课程成本高。
- 验证：以“新增一个页面需要改几处”为度量。

### ADR-04 定时任务：进程内线程还是外部调度

- 背景：NFR-03、P-15；单进程线程在 `app.py:4971`。
- 备选 A：保留线程。代价：多 worker 重复执行；收益：零依赖、随应用启动。
- 备选 B：外部调度（Windows 计划任务/APScheduler 独立进程）+ 数据库锁。代价：多一个部署单元与锁设计；收益：可观测、可重试、不阻塞 Web 进程。
- 验证：启动两个 worker，观察是否重复生成违约/通知。

### ADR-05 不变量位置：应用层还是应用层+数据库触发器

- 背景：预约重叠、违约去重、审计不可改删已有触发器。
- 备选 A：维持双保险。代价：错误信息需在应用层翻译；收益：并发兜底强。
- 备选 B：只保留应用层。代价：并发/直连 SQL 可破坏不变量；收益：逻辑集中。
- 验证：并发抢座、重复扫描、直连 SQL 改审计三类测试。

### ADR-06 参数来源：`config.py`、`rule_params` 表还是两者

- 背景：默认值在 `config.py`，运行时读表，旧库不迁移。
- 备选 A：维持双源，补一条“启动时对缺失参数补种/对新增参数补种”的迁移逻辑。代价：需定义“代码默认值 vs 业务当前值”的优先级。
- 备选 B：只保留表，代码不存默认值。代价：首次建库需外部初始化数据。
- 备选 C：只保留 `config.py`。代价：无法后台配置，违反 FR-13。
- 验证：修改默认值后重启旧库，检查参数是否变化。

### ADR-07 审计防篡改：应用+触发器是否足够

- 背景：BR-24、AC-14-03；当前任何有文件权限者可改库。
- 备选 A：维持。代价：防篡改边界只在应用内；收益：零成本。
- 备选 B：只读账号/独立库/哈希链/异地副本。代价：部署复杂度；收益：可举证。
- 验证：以“普通运维权限能否改一条审计”为验收问题。

### ADR-08 认证：模拟账号还是 SSO 适配层

- 背景：FR-01 要求校内统一身份认证；当前本地账号。
- 备选 A：明确“课程演示用模拟 SSO”，在基线中写清替换点。代价：与 FR-01 原文有差距；收益：可交付。
- 备选 B：抽象 `AuthProvider` 接口，先实现本地适配器，预留 SSO 适配器。代价：多一层抽象与测试；收益：未来替换成本低。
- 验证：替换适配器后，登录/角色映射/锁定逻辑是否不变。

- 冲突点：NFR-05 要求并发抢座只成功一条；当前用 SQLite 写锁 + 触发器，单机正确，但单写者无法支撑 NFR-04 的写入吞吐；测试为顺序调用，未做多连接并发验证。

- 方案 B：换 PostgreSQL，用唯一/排他约束与连接池。代价：部署与迁移成本；收益：更接近生产语义。

- 冲突点：FR-01 功能要点 3 要求学生单会话、管理员可多端但关键处置需二次确认；NFR-10 要求手动违约、黑名单解除、座位停用二次确认。代码无单会话；只有解除黑名单/复核/取消/签退有前端 `confirm`，手动违约与停用/恢复没有。
- 依据：FR-01、NFR-10、权限矩阵 ▣；`templates/*.html` 的 `confirm` 搜索。
- 方案 A：补服务端单会话与关键操作二次确认（一次性令牌/确认参数）。代价：会话表、接口字段与前端改动。
- 方案 B：保留前端 `confirm`，并把“单会话”标为未实现。代价：可被绕过，验收风险。
- 影响阶段/任务：S1、S3；T-E。
- 状态：待人工确认。

#### Q-38 用户信息管理

- 方案 A：补本人联系方式修改与系统管理员用户查询（含审计）。代价：新增接口、脱敏与权限测试。
- 方案 B：明确本期只做评价，用户信息管理移出范围。代价：FR-08 不完整。
- 影响阶段/任务：S5；T-B。
- 状态：待人工确认。

#### Q-39 数据分析维度与口径

- 冲突点：FR-11 要求使用率、时段、院系分布、近 7/30 日趋势、待受理投诉数等；代码只有按自习室预约量/违约量柱状图、逐日折线、6 类统计，没有使用率、时段、院系，日期范围由页面默认 7 天但接口可传任意区间。
- 依据：FR-11 功能要点 1—5、AC-11-02—04、Q-15/OQ-30；`app.py:3825-3985`。
- 方案 A：维持现有维度，在需求/验收中改写为“按自习室 + 日粒度”。代价：需修改 AC 措辞。
- 方案 B：补齐使用率、时段、院系维度（需座位时长口径与院系字段聚合）。代价：统计定义与测试工作量增加。
- 影响阶段/任务：S6；T-B。
- 状态：待人工确认。

#### Q-40 账号状态单字段与双维度

- 冲突点：DM-04 账号状态只有正常/黑名单/锁定；1.4 与 BR-25 又称锁定与黑名单互不影响；代码用 `pre_lock_status` 保存进入锁定前的状态，解锁时恢复。
- 依据：DM-04、SM-03、BR-25、OQ-04；`schema.sql:15-23`、`app.py:1410-1422`。
- 方案 A：保留单字段 + `pre_lock_status` 的现有口径，并在数据字典中说明。代价：叠加态展示不直观。
- 方案 B：拆为 `blacklist_status` 与 `lock_status` 两个独立字段。代价：迁移、状态机与页面改动。
- 影响阶段/任务：S1、S2；T-B。
- 状态：待人工确认。

#### Q-41 黑名单解除后计数

- 冲突点：与 Q-06 同源，但影响架构：`users.effective_violation_count` 是持久计数，解除黑名单不清零；再次违约会立即触发新黑名单。
- 依据：BR-12、ST-21/ST-22、Q-06/OQ-15。
- 方案 A：维持不清零，并在信用页明示“计数继续累计”。代价：用户体验与申诉量可能上升。
- 方案 B：解除时清零或按周期衰减（需审计与重算）。代价：计数语义变化，历史记录与当前计数可能不一致。
- 影响阶段/任务：S2；T-D。

#### Q-42 无有效预约时 V3 的登记对象

- 依据：UC-10 A3、BR-11、DM-07、OQ-20。
- 方案 A：维持“必须提供学号”。代价：现场无法确认身份时不能登记。
- 方案 B：允许登记到“未知人员/座位”占位对象，后续认领。代价：新增对象模型与申诉/计数归属规则。
- 影响阶段/任务：S3；T-B。
- 状态：待人工确认。

#### Q-43 停用“使用中”座位

- 依据：ST-08、AC-02-04、OQ-21。
- 方案 A：维持“当前使用不强制终止”。代价：停用座位仍可能被占用一段时间。
- 方案 B：立即终止当前使用并生成处置记录（需定义是否违约、通知与审计）。代价：业务争议与实现复杂度。
- 影响阶段/任务：S3；T-B。
- 状态：待人工确认。
